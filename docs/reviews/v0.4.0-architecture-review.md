# v0.4.0 architecture review

A review of the whole generated application, with most attention on what v0.4.0 added:
`--Auth none|identity|saas`, organisations with multi-tenancy, roles and invitations, and the
pre-rendered public pages. Reviewed on 2026-11-27, at commit 637870a, before v0.4.0 was released.

The overall design holds up. Tenancy lives in the persistence layer, the access token names the
organisation, and membership is checked on every request. As a result, an endpoint can't leak
another organisation's Todos by forgetting a filter. The review found one serious hole that
predates v0.4.0 (finding 1) and several v0.4.0 bugs.

| # | Finding | Severity | Status |
|---|---|---|---|
| 1 | Email links are built from the request's `Host` header | High (predates v0.4.0) | Fixed |
| 2 | A removed member's SignalR connection keeps receiving the organisation's updates | High | Fixed |
| 3 | After losing access, the browser repeats the user's request in another organisation | Medium | Fixed |

## Fixed

### 1. Email links used the request's `Host` header

**Problem.** `ClientUrl.For` built the links in emails from `App:ClientUrl`, falling back to
`Request.Host`. Only `appsettings.Development.json` set `App:ClientUrl`, and `AllowedHosts` was
`*`. So anyone could ask for a password reset for someone else's account, with
`Host: evil.example`. The victim would get a genuine email whose link sent the reset token to the
attacker's site, giving the attacker the account.

The same happened to confirmation, email-change and admin invitation links. It also affected the
redirect after Google or GitHub sign-in, which carries the new session's tokens in its URL. v0.4.0
added organisation invitations to the same path. A stolen invitation token is enough to create
the invited person's account, already confirmed.

**Fix.**
- `Identity/ClientUrl.cs`: `ClientUrl.Validate`, called at startup from `AddIdentityJwt`, stops
  the app from starting outside Development unless `App:ClientUrl` is an absolute http(s)
  address with no query or fragment. Development still falls back to the API's own address.
- `deploy/docker-compose.yml` sets `App__ClientUrl: https://${DOMAIN}`, and CI's "Publish and
  run" step sets `App__ClientUrl: http://localhost:5000`.
- `docs.app/deployment.md` lists the setting and explains why. It also says to refuse requests
  for other host names: the Caddy setup already does, and without it you set `AllowedHosts`.
  `docs.app/security.md` mentions the setting too.
- Tests (`tests/ApiHost.Tests/ClientUrlTests.cs`):
  - Links use the configured address whatever the `Host` header says.
  - The app refuses to start with a missing or invalid address outside Development.

**Still open.** `robots.txt` and `sitemap.xml` (`ClientAppHosting.MapSearchEngineFiles`) still
use the request's host. That matters little: they carry no secrets, and refusing other host names
covers them.

### 2. SignalR connections outlived their access tokens

**Problem.** A request's access token is checked when it's validated, including whether the user
is still a member of the token's organisation (`OrganisationSetup`). A SignalR connection is only
authenticated when it opens, and `MapWolverineSignalRHub` maps the hub with no options. A removed
member's open tab therefore stayed in the `organisation:{id}` group for as long as it was open. It
kept receiving `TodoChanged`, and `TodoReminder`, which includes the Todo's title. The same was
true in `identity` mode for a deleted or locked-out account.

**Fix.**
- `Program.cs` maps the hub with `MapHub<AppHub>(..., options => options.CloseOnAuthenticationExpiration = true)`
  whenever there are accounts. (`MapWolverineSignalRHub` only calls `MapHub`.) The server closes
  each connection when its access token expires.
- Reconnecting runs the membership check again, so a removed member is out within one access
  token lifetime (15 minutes by default).
- `features/todos/useTodoRealtime.ts`:
  - The connection's token comes from `freshAccessToken`, which refreshes a token that has
    expired or will within 30 seconds.
  - If the connection closes for good, it's started again after 5 seconds, until that works, and
    the Todo list is refetched. That covers a close for an expired token, which SignalR's
    automatic reconnect doesn't retry, and automatic reconnect giving up.
- Tests:
  - `TodoRealtimeTests.the_hub_closes_connections_when_their_access_token_expires` checks the
    hub's options.
  - `useTodoRealtime.test.ts` checks `freshAccessToken`.

**Still open.** For up to one access token lifetime after removal, the removed member can still
receive live updates (Todo ids, and the titles in reminders). Closing their connections at once
would need the server to track which connections belong to which user, across every instance.
That's worth doing if a shorter window matters.

### 3. The browser repeated requests in another organisation

**Problem.** When a request got a 401, `lib/api/client.ts` refreshed the tokens and sent the
request again. If the 401 meant "no longer a member", the refresh moved the session to another of
the user's organisations (`OrganisationAccess.ChooseAsync`), and the request was repeated there.
For example, a member removed while typing a Todo who then pressed Add had the Todo created in
their other organisation, with nothing to say so.

**Fix.**
- `lib/api/client.ts` compares the organisation of the token the request was sent with against
  the token after the refresh (`organisationIdOf` in `lib/api/authTokens.ts`). If they differ, it
  returns the 401 without repeating the request and tells `onOrganisationLost` listeners.
  Without organisations both are null, so nothing changes in the other modes.
- `features/organisations/OrganisationSwitcher.tsx` shows an alert in the header: the user no
  longer has access to the organisation they were working in, their last change there wasn't
  saved, and which organisation they're in now. The cached data is already dropped when the
  organisation changes.
- Test: `client.test.ts`, "doesn't repeat a request in another organisation after losing access
  to the first".

### 4. Deleting an organisation and deleting its data weren't one transaction

**Problem.** `OrganisationStore` gets its own `IDocumentSession` or `AppDbContext` through service
location and saves each change straight away. That is outside Wolverine's unit of work, so the
deletion endpoint committed the deletion first. `OrganisationDeleted` went out afterwards, as a
returned message. `LeaveOrganisationsOfDeletedAccountHandler` worked the same way.

A crash between the two left the organisation gone but its Todos and their event streams kept for
good. Nothing could start the clean-up again, which broke the promise that deleting an
organisation deletes its data.

**Fix.** `IOrganisationStore.DeleteAsync` now publishes `OrganisationDeleted`, for the
organisation's tenant, through Wolverine's outbox in the same transaction as the deletion:
- Marten: `IMartenOutbox.Enroll(session)`, `PublishAsync`, then `SaveChangesAsync`.
- EF Core: `IDbContextOutbox.Enroll(db)`, `PublishAsync`, then `SaveChangesAndFlushMessagesAsync`.
  The organisation's rows are loaded and removed, rather than deleted with `ExecuteDeleteAsync`,
  which would run immediately, outside that transaction.

The endpoint and the account-deletion handler no longer send the message themselves. The existing
tests for deleting an organisation, and for deleting an account, still check that the Todos go.

**Still open.** Other changes the store makes still commit separately from any messages sent with
them. The one that matters is an invitation: it's saved, then `SendOrganisationInvitation` is
sent, so a crash between them leaves an invitation listed whose email was never sent. Inviting
again fixes it.

### 7. Sign-in failed for long emails on EF Core `saas`

**Problem.** A new user's own organisation was named after their display name or, without one,
their email (`OrganisationAccess.ChooseAsync`). The EF Core `Name` column holds 100 characters
(`OrganisationNames.MaxLength`), but an email can be up to 256. Every sign-in by a user with a
longer email and no display name failed with a database error.

**Fix.** The name is cut to `OrganisationNames.MaxLength`.
Test: `OrganisationTests.a_new_account_with_a_long_email_gets_an_organisation_named_within_the_limit`.

## Open

### 5. Invitations can be used to send spam or phishing

Anyone can register, create an organisation and send any number of invitations. Each one is an
email from the app's domain, with the subject "Join {organisation name}", a name the sender
chooses. Suggested fix: limit `POST /api/organisation/invitations` per user and per organisation,
and cap pending invitations per organisation. This fits with v0.4.1's plan limits, but the abuse
is possible from v0.4.0.

### 6. Invitation tokens are recorded in traces

`GET /api/join/{token}` puts the invitation's secret in the URL path. OpenTelemetry's ASP.NET Core
instrumentation records `url.path`, so anyone who can read the traces can use the invitation.
Suggested fix: `POST /api/join/details` with the token in the body, as the other account tokens
are sent.

### 8. Two changes at once can leave an organisation without an owner

`OrganisationRules.CanChangeRole` and `CanRemove` count the owners, and then the change is saved
in a separate step. Two owners demoting each other at the same moment can leave none. The same
can happen if someone accepts an invitation after `DeleteAccountEndpoint`'s check but before
`LeaveOrganisationsOfDeletedAccountHandler` runs. Suggested fix: check and change in one
transaction, with a row lock or a serializable transaction, or check again after saving.

### Smaller points

- `LeaveOrganisationsOfDeletedAccountHandler` relies on `MembersAsync` joining to users. The
  deleted user is already gone, so an organisation they were alone in has no members. That's
  correct but fragile: counting memberships directly would be clearer.
- Reminders go to everyone in the organisation, not only the person who set them. It's probably
  better to keep reminders personal.
- In `saas`, Todos keep their `OwnerId` after the account is deleted, including in their events.
  That's defensible, since the data belongs to the organisation, but `accounts.md` should say so.
- Expiry checks use `DateTimeOffset.UtcNow` in the stores, the join endpoint and the invitation
  email handler, but `TimeProvider` in `OrganisationAccess`. Using one would let tests control
  time.

## Structure

- **Combinations:** the number of template combinations is becoming the main cost of changing the
  template. Some files have three-way `#if` blocks in method signatures (`RemindTodoEndpoint`,
  `TodoNotifications`), and v0.4.1's billing will add more.
- **`identity` as a hidden single-user organisation:** worth deciding before v0.4.1. Every user
  would have one personal organisation and no switcher.
  - `identity` would then get the same tenancy-based isolation as `saas`. Today it relies on
    `OwnerId` checks written into each endpoint: exactly the "forgot a filter" risk that `saas`
    removes.
  - Most of the per-user branches would go too.
- **What works well:**
  - One `TokenIssuer` for every sign-in and refresh.
  - Invitation tokens are created when the email is sent, so they're never in Wolverine's message
    tables.
  - Deleting an organisation fans out through `OrganisationDeleted`, and each feature deletes its
    own data.
  - The CSP allows exactly the build's inline scripts, by hash.
  - The `Name.Marten.cs`/`Name.EfCore.cs` split keeps the per-persistence code readable.
